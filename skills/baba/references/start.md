# Start an app

Start in the build util: write the app's brief with the person, and once they approve it, `create` makes the app. It copies assets/template into skills/NAME in the project, names the framework in its package.json at the release this skill depends on, puts the app's name in place and keeps the brief beside them as brief.json. It then links the app from .claude/skills/NAME and .agents/skills/NAME, which installs it in this project. A project's own apps live in skills/; the authoring app finds an app by its SKILL.md and its door, scripts/open.ts, anywhere in the project outside the harness's own folders, so it lists every app there, and neither the installed copies nor a skill that is no app. The app holds no framework: it depends on the npm package babavoss at an exact version, and imports it as babavoss/core/… and the shell as babavoss/shell/….

The new app runs as it is: a shell of one util, always open, whose page shows the surface and offers the person one decision. Open it with `bun <its directory>/scripts/open.ts` and give the person its page before changing anything. The door installs what the app depends on before it first opens, the framework from the babavoss repository on GitHub, and says so only when that fails; pass that line to the person. Then replace the template's greeting with the app's own work, step by step.

A running app takes a change by itself. Changed code under src/ is loaded into the running runtime once nothing runs, or after a bounded wait that cuts what still runs: the address stays, the state is restored from what was saved, and the person's open page goes on. The next answer begins with a line when the change waits, was loaded after waiting or cutting, or did not start; code that does not load leaves the code before it running, so read the app again after an edit and check that the change is there. When the page's own code changes, the open page loads again by itself. Do not close the app to load a change.

Give the app a description. Its version is the semantic version in package.json, set by hand. Its one entry is scripts/open.ts. Keep SKILL.md at the root; put further know-how in references beside it.

Write the skill to the agent. Its description says what the app does and when to use it, as a phrase and a "use when", never a sentence about the skill. Add `compatibility: Requires Bun 1.4 or later` to its frontmatter. Keep the template's opening and its "Operating it" section as they are: they are the same in every app, and they are what the agent knows before its first command. Under them write the app's own part: the order of the work, who decides what, and when not to act, which is the judgement the surface cannot express. What is mechanical belongs in the surface: what an input may be, in the handle's description and in the view that offers it; what must be waited for, as a fact. In a playground trace, a refusal, or a read that led to no action, is something the skill or the surface should have said. Exact commands come from the door's answer; never write them into the skill. Do not assume the agent has these authoring references.

Design the [surface](surface.md) first, then its [page](page.md). The template's spec/app.spec.ts is the app's first story: replace it with one test per rule as you write each rule, and run them with `bun test`. Keep the door and bv as the agent's way to operate the app. An app uses its harness's skills and shell; it imports no harness adapter.

Open the authoring app in the project. Inspect the description, skill text and open answer in the promptware util after changing them or the root view. It shows the description, skill body without frontmatter, references and open answer, with character counts and token estimates of one token per four characters; the open answer is computed by running the app's own cli. Keep the text sufficient for the work and small enough to read each time.

Write a [scenario](playground.md) for the first task and try it with the person. Confirm that open gives the whole view and page address, a call through bv changes the page, and a person call appears in the next answer.

To install an app somewhere else, put its directory among that harness’s skills. Install baba itself with `bunx skills add alanremarc/babavoss -g` for every project, or without `-g` from a project's directory for that project. Update it with `bunx skills update baba`. An app is updated by replacing its directory: when it opens at a newer version than it last did, its door says so once and points to the app’s CHANGELOG.md, so write there, newest first, what each version changed for the person and the agent.

The framework an app depends on follows this skill, which carries the know-how for it. An app keeps the version it names until it is raised: when this skill is at a later one, its door says so once in the project of that app. On the person's word, read this skill's CHANGELOG.md for what changed, set the app's `babavoss` to the release this skill names, `github:alanremarc/babavoss#vX.Y.Z`, in its package.json, run `bun install` there, adapt the app, and verify its saved state, skill, open answer and scenarios again. Never raise an app past this skill's version.

Contribute a framework fix upstream as a pull request to the babavoss repository, under packages/babavoss. To try one before it is released, name a checkout in the app's package.json in place of the release, as `link:` or `git+file://` with no version tag, and put the release back after.

Check an app with `bun check` and `bun test`; it needs no other tool. Write its code in the framework's style, which no tool enforces: no semicolons; double quotes; lines up to 160 columns; an object, array or call that fits on one line stays on one line; trailing commas where a list spans lines; a blank line before a return, and before and after a group of const and let declarations; no `any`; every file opens with a comment that says what it is for.
